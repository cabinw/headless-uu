## 探针如何判定结果

Python 探针的正常数据传输用例按约定长度接收合成 TCP 数据，校验 SHA-256，并检查连接结束。客户端写入或 `drain()` 返回仅代表本地写入进度；目标完成写入也不证明客户端已收全。这些探针的正常流不依赖 TCP 半关闭，不调用 `shutdown(SHUT_WR)` 或 `write_eof()`；预期的目标关闭是完整关闭。

为区分发送完毕与接收完毕，新增三种目标关闭方式。默认 `immediate` 保留旧探针语义；`delay` 在发送后额外等待 250 毫秒；`ack` 等客户端完成数据校验并发回 44 字节的合成应用确认后关闭，确认等待上限为 30 秒。应用确认包含仅用于合成流的标识与哈希，不是 UU 的 DATA_ACK，也不是面向任意 SSH/TCP 服务的生产修复。

客户端和目标分别记录安全的合成流编号、收写字节数、阶段及关闭等待结果。关闭等待超时与连接重置异常分开计数。离线自检 9 项通过；本机回环的三种关闭方式共 21 组、690 条流按各自预期通过，覆盖小数据、smoke、大数据传输、64 路并发、慢读、异常断开和连续建流。其中预期异常断开的用例以重置/关闭行为验收，不计为完整负载哈希通过。这证明对照工具在该本地负载下可用，不能替代官方客户端验证。

### 可复现工具与使用边界

本轮此前实测使用的原版探针 SHA-256 为 `2fb02c840a27ba3379f3a2a115b960199c5675f7e920c611d8ef4b40c8ebc54b`，其私有原文件保持不变。仓库中的 [`tests/support/tcp_mapping_probe.py`](../tests/support/tcp_mapping_probe.py) 在该版本基础上增加了 `--concurrency-size-bytes`、相应计划字段和离线校验，用于区分连接数量与突发数据量；新版 SHA-256 为 `245c1bb188cabcb8271208a3074061b08eb2d4f8d68122a8aa0c63ef25c9d6af`。新参数仅改变 `concurrency` 场景的每流负载，范围为 1 字节至 16 MiB，默认仍为 512 KiB，其他默认值和线协议不变，原服务端无需更换。

原版离线 `selfcheck` 为 9 项；新版增加两项并发负载与预算校验，共 11 项通过。新版 `plan` 验证了原默认 64×512 KiB、立即关闭的预算仍为 67,110,848 字节，64×64 KiB、应用 ACK 的预算为 8,393,408 字节。自检覆盖编码、确定性数据、预算和模拟 writer 的关闭行为，不是 TCP 或 UU 兼容性测试。工具需要 Python 3.9 或更高版本，只使用标准库，不读取文件、账号配置或环境变量，不执行 shell，也不进行登录或云上传。

从仓库根目录可先做离线检查和负载规划；这两个子命令不创建网络连接：

```sh
python3 tests/support/tcp_mapping_probe.py selfcheck
python3 tests/support/tcp_mapping_probe.py plan --scenario single --size-bytes 63 --rounds 20 --concurrency 1 --max-mib 1 --close-mode immediate
python3 tests/support/tcp_mapping_probe.py plan --scenario concurrency --concurrency 64 --concurrency-size-bytes 65536 --max-mib 16 --close-mode ack
```

最后一条规划保留 64 个连接，将合成负载降为每流 64 KiB、每方向合计 4 MiB；默认并发场景则为每流 512 KiB、每方向合计 32 MiB。`--size-bytes` 仍只用于 `single` 场景，不能代替新的并发负载参数。

做本机回环对照时，在一个终端启动限时目标，在另一个终端运行客户端：

```sh
python3 tests/support/tcp_mapping_probe.py serve --port 42821 --max-seconds 180 --flow-seconds 60 --max-active 16 --max-connections 100 --max-mib 64
```

```sh
python3 tests/support/tcp_mapping_probe.py client --port 42821 --scenario single --size-bytes 63 --rounds 20 --concurrency 1 --max-seconds 60 --flow-seconds 45 --max-mib 1 --close-mode immediate
```

将最后一个参数分别改成 `ack` 和 `delay` 可做关闭方式对照。官方客户端验证需先获得相应现场授权：在受控宿主启动同一目标，由官方客户端将其回环目标映射到本机端口，再将探针客户端的 `--port` 设为该本机映射端口。工具本身不部署服务、不创建 UU 映射，也不读取或改变官方客户端状态。不要将它指向 SSH 或其他业务协议；客户端核验固定 banner 后才发送合成头和负载，这只是防误连措施，不是认证机制。

监听和连接地址均固定为 `127.0.0.1`。单流负载最多 16 MiB，客户端并发最多 64；总负载预算、目标准入数量和各阶段时间均受参数约束。`--max-mib` 预算按合成应用字节预留，不包含 TCP/IP、UU 封装或重传，也不是 RSS 上限；收尾的关闭等待可能增加总耗时。目标超过 `--max-connections` 后继续接受并拒绝新连接，该值不是系统 accept 次数的硬上限；此工具用于受控合成负载，不是面向不可信本机连接洪水的服务。测试默认遇到失败阶段就停止后续阶段，不能把未运行的场景计作通过。

文中传输阶段在 120 秒期限后结束的流，由合成目标自身的 `--flow-seconds` 期限终止并关闭；这不是 daemon 在 120 秒后自动回收未收到 FIN 的残留流。当前宿主转发循环没有同等的通用空闲回收期限。若官方客户端未发送 FIN，而真实目标持续保持连接且没有其他关闭或 I/O 错误，不能从这些探针结果推断它会自动释放；已证明的残留流清理手段是关闭相应 peer/session，不能用合成目标的超时掩盖这一边界。

结果必须按两端和测试目标解读：

| 字段/结果 | 含义与验收边界 |
|---|---|
| 客户端 `data_verified=true` | 该正常数据流完成了负载哈希校验；不能用预期中止用例的 `outcome=ok` 替代 |
| 客户端 `result.passed=true` / 退出码 0 | 客户端用例按预期完成；不代表目标收到了应用 ACK，也不代表关闭等待没有异常 |
| 目标 `completed` | 目标已产出该流数据；在应用 ACK 等待之前增加，不是端到端交付确认 |
| ACK 模式 | 按合成 `flow_id` 和测试时间窗对应两端；目标应为 `stage=acknowledged` 且 `outcome=ok`，相应 `acknowledged` 数量匹配、`ack_timeouts=0`。目标确认超时后关闭仍可能使客户端得到 EOF 并报告通过 |
| 关闭可靠性 | 正常流需另查双方 `close_wait_timed_out`、`close_wait_error`、`close_forced_abort`；这些标记不会自动把客户端 `outcome=ok` 改成失败。预期重置用例单独统计 |
| 目标 `serve` 退出码 0 | 目标服务正常结束运行；不代表其间所有流均通过，仍须检查流记录和汇总 |

输出仅包含合成流编号、枚举/布尔状态、长度、计数、时间与合成哈希摘要，不输出转发负载、账号配置、令牌或异常原文。合成 `flow_id` 不是 UU 的真实会话标识，且每次客户端运行重新计数，因此跨批次关联必须同时限制时间窗。公开实测应使用汇总证据，不附真实账号资料或官方客户端原始日志。

## 宿主队首阻塞：独立复现与修复

旧实现处理未知流 DATA 和无效 SYN 时，会等待发送相应 FIN 或失败 SYN_ACK。若共享出站队列已满且发送端停滞，这次等待会占住 FILE 数据通道的接收回调，使后续流的 SYN、DATA 或 FIN 无法及时处理。

本次先用回归测试复现失败，再将这类控制响应交给有界调度器，合并同一流重复的待发 FIN，并保留原有出站顺序及取消关联。会话关闭或释放时必须结束调度任务；不同身份的控制响应超过容量时，关闭受影响的 FILE 通道，并验证其他通道和独立映射会话仍可工作。没有通过无限创建任务或无限扩大队列来回避拥塞。

HOL 修复阶段新增 7 项回归，覆盖共享接收可继续处理、重复响应有界、正常 EOF 后重复 FIN 合并、调度任务释放、诊断任务释放及通道/会话隔离。随后新增一项真实 SCTP 并发回归；最终 macOS 与 Linux 均为 91 项单元测试加 6 项 CLI 测试，各 97 项全部通过。

这项并发回归在本地虚拟网络上建立真实 DTLS/SCTP，并使用真实回环 TCP 目标，逐字节检查回显与 FIN 顺序：先让 64 条流各传输 128 KiB，合计每方向 8 MiB；再向 8 条在途流发送 FIN，立即复用相同流标识，各传输 63 字节；最后关闭 peer，重新建立 DTLS/SCTP，让 64 条流各传输 32 KiB，合计每方向 2 MiB。每条正常流额外有 4 字节长度前缀，也纳入逐字节检查。新增并发回归仅在 `cfg(test)` 中运行，不改变 daemon 的运行代码。

这些测试证明被覆盖的宿主处理、完整性与清理时序通过；本地重新建立 peer 不是官方客户端或云信令重连验收，现场 64 路、慢读和异常断开后的结果仍另行统计。

## 提前关闭对照

本节和下一节的现场数据均来自 HOL 修复前的 debug 诊断候选；候选增加诊断计数，不包含本轮 HOL 修复。它们不是修复后或 release 构建的验收结果。

基线 smoke 为 7/8；其中 63 字节回显测试仅收到 7 字节 banner，尚未收到回显负载就遇到连接结束。随后使用同一合成协议对照目标关闭方式：

| 负载 | 立即关闭 | 等应用确认后关闭 | 额外等待 250 毫秒后关闭 |
|---|---|---|---|
| 63 字节回显，20 次 | 17/20 通过 | 20/20 通过 | 20/20 通过 |
| 4 MiB，客户端慢读 | 收到 3,846,151 / 4,194,311 字节，未完成校验 | 收全 4,194,311 字节，哈希通过 | 收到 3,510,279 / 4,194,311 字节，未完成校验 |

表中的接收长度包含 7 字节 banner。它们是 TCP 应用负载，不是单个 SCTP 帧。对应 63 字节和慢读样本中，宿主 `target_read`、`queued_data`、`dc_sent_data` 均记录了完整数据长度，期间未关闭映射会话；目标正常关闭的等待没有超时或强制中止。这组完整的读入、排队和发送计数，以及关闭状态，不支持“宿主队列丢掉余下 DATA”或“探针关闭等待超时后强制中止”这两种解释。数据通道发送成功仍不证明数据已从官方客户端完整交付给本地 TCP 接收方。

这些样本的 `cancelled_data` 也为零，但该计数只覆盖出站 worker 取出 DATA 后因取消令牌而跳过的字节；会话 shutdown 直接丢弃队列等路径不全部计入。因此单独一个零值不能证明没有丢弃，不能脱离完整计数链及会话状态使用。

应用确认模式改变了关闭时序，小包和这次慢读对照均收全；固定延时未稳定消除慢读截断。这个结果有助于定位关闭竞争，但不能要求实际目标服务实现探针确认协议，也不能据此承诺任意固定延时都足够。

## 64 路并发与确认到达的区别

每条流发送 512 KiB 并接收同样长度的回显，64 条流共上传 32 MiB、下载 32 MiB，另有少量探针头、banner 与应用确认。负载是分块 TCP 数据，不能与单次数据通道发送大小混淆。

原接收窗口的诊断候选在应用确认模式下得到客户端 31/64 通过。将宿主 SCTP 接收缓冲实验性增至 8 MiB 后，同负载为 22/64；其中 21 条在目标端确认收到应用确认，1 条在目标端确认等待超时，另有 42 条在目标端传输阶段超时。该扩大缓冲的实验已撤销。两次有限样本不证明窗口大小与失败率的确定关系，也未解决问题。

将原窗口测试的客户端与目标记录按合成流编号和时间窗对应后，31 条“客户端通过”进一步分为两组：

| 流数 | 客户端结果 | 目标结果 | 前后关系 |
|---|---|---|---|
| 14 | 完整回显、哈希通过 | 收到并校验应用确认，正常关闭 | 目标约 55.42–55.53 秒结束，客户端约 55.56–55.68 秒结束 |
| 17 | 完整回显、哈希通过 | 已发送完整回显，但 30 秒内没有收到应用确认，确认等待超时后关闭 | 目标结束比客户端结束早约 40–147 毫秒；客户端总耗时约 35.64–50.77 秒 |
| 33 | 只收到 7 字节 banner，提前连接失败 | 只收到部分上传，仍处于传输阶段，最终到达 120 秒流期限 | 客户端约 6.00–11.40 秒失败；目标在其后约 108.60–114.01 秒才超时 |

17 条确认超时流的客户端记录了确认写入本地连接，但目标接收计数没有对应的 44 字节确认。因此“31 条客户端通过”不等于“31 条应用确认送达”。33 条失败流也不是目标先到达 120 秒期限才引起客户端失败。不同主机时钟未做精密校准，毫秒级间隔只用于描述日志对应；百秒级先后差足以区分上述两种结束过程。

## ThinkPad：HOL release 首轮双端结果

本节使用上表所列 HOL release 产物，与前两节的修复前 debug 诊断候选分开统计。该轮主服务 CPU、内存和任务数配额为无限；合成探针单独限制为 CPU 50%、内存 256 MiB、任务数 128。实际连接为 `route=direct`，两端使用 UDP，候选类型为 host/prflx。CONTROL、TEXT 和 FILE 通道均记录 `ordered=true`、`max_packet_lifetime=0`、`max_retransmits=0`；这些是实现输出的协商参数，不是零丢包或零提前关闭的证明。

| 场景 | 客户端结果 | 目标端核对与边界 |
|---|---|---|
| 64 路，每流 512 KiB 回显，应用 ACK 模式 | 64/64 完整哈希通过；15.631 秒；无未完成项或总期限触发 | 64/64 应用 ACK 实达；无 ACK 超时、流超时或关闭等待异常 |
| smoke，立即关闭 | 8/8 完整哈希通过；0.256 秒 | 8 条均产出完整数据并正常关闭 |
| abort，立即关闭，独立运行三轮 | 30/30、29/30、29/30；合计 88/90 | 60 条为预期重置行为；恢复数据流为 28/30 哈希通过，另 2 条截断 |
| abort，应用 ACK，独立运行三轮 | 每轮 30/30，合计 90/90 | 60 条为预期重置行为；恢复数据流 30/30 完整哈希通过且目标收到全部 30 个应用 ACK |
| 4 MiB 客户端慢读，立即关闭 | 0/1；收到 1,114,119 / 4,194,311 字节；1.615 秒结束 | 目标已提交完整 4,194,311 字节并正常关闭，客户端未收全 |
| 4 MiB 客户端慢读，应用 ACK | 1/1；收全 4,194,311 字节、哈希通过；5.911 秒 | 目标收到并校验应用 ACK，正常关闭 |
| churn，应用 ACK 模式 | 101/101；1.556 秒 | 前 100 条仅连接后关闭，最后 1 条为完整恢复流，哈希和目标 ACK 均通过 |

六轮 abort 分别启动客户端，每轮计划和实际均为 30 条，没有因某轮失败而漏跑后续轮次。两条立即关闭恢复失败均为 4,096 字节回显只收到 7 字节 banner；目标分别收到了完整的 4,120 字节请求（24 字节头加负载），并提交了完整的 4,103 字节响应（banner 加负载）。两条目标的关闭等待均无超时、错误或强制中止。慢读立即关闭样本也没有目标关闭等待异常。因此 HOL 修复加 release 构建仍未消除真实客户端上的关闭尾部截断，不能将应用 ACK 对照的通过结果描述成通用生产修复。

64 路应用 ACK 样本的字节计数在两端对应：客户端发送、目标接收均为 33,558,784 字节；目标提交、客户端接收均为 33,554,880 字节。前者包含每流 24 字节头及 44 字节应用 ACK，后者包含每流 7 字节 banner。宿主 64 条流均以 `target_eof` 释放，`rx_data_bytes=target_written=33,558,784`，`target_read=queued_data=dc_sent_data=33,554,880`。这里的交付结论来自客户端完整哈希与目标 ACK 两端核对，不是仅凭 `dc_sent_data`。

这一批共对应目标端 355 条流，最后活动数为 0；应用 ACK 实达 96 次，分别是 64 路并发、30 条 abort 恢复、1 条慢读和 1 条 churn 恢复。目标无流超时、ACK 超时、协议错误、内部错误、准入拒绝或关闭等待异常。目标统计的 60 次主动重置，以及 160 次对端提前结束（60 次预期客户端重置、100 次仅连接后关闭），属于设计中的场景。目标 `completed=135` 是产出完成数，其中三条客户端未收全；不能将它写成 135 条端到端哈希通过。

首轮本批未运行 1/4/8 MiB 大数据矩阵、其余三种慢读/慢写场景或 64 路立即关闭对照；表中两个慢读用例各仅一条。后续恢复 release 的 64 路立即关闭结果单列于下文，没有把首轮未执行项计为通过。

## 腾讯：HOL release 实际 relay 路径

腾讯候选使用同一 HOL release 产物，实际路径为 UDP relay/relay。CONTROL、TEXT 和 FILE 通道均记录 `ordered=true`、`max_packet_lifetime=0`、`max_retransmits=0`。候选 CPU 配额为 100%，即一个逻辑 CPU 的时间带宽，内存限额 256 MiB、任务数上限 128、CPUWeight 为 10；探针为 CPU 50%、256 MiB、128 个任务、CPUWeight 10。不能把 ThinkPad 直连上的通过项直接外推到这条中继路径。本节先记录默认每流 512 KiB 的 64 路测试及随后 basic 批次，均使用原版探针；新增参数后的 64×64 KiB 对照另行统计。

### 64 路、每流 512 KiB

64 个连接共计划每方向 32 MiB 合成负载，应用 ACK 模式下客户端完成 64 条，其中 11 条完整哈希通过、53 条连接失败，总耗时 29.752 秒；没有未运行项或客户端总期限触发。失败流分别只收到 7 至 98,311 字节（包含 banner），不是已经完整接收后才发生的哈希不一致。客户端的 53 条失败记录了关闭强制中止，关闭等待超时数为 0，两者不能混淆。

目标端确认 11 个应用 ACK 实达；另 53 条只收到部分上传，停留在传输阶段，最终由合成目标的 120 秒期限关闭。该释放时间来自目标探针，不是宿主自动回收未收到 FIN 的残留流，也不能据此承诺真实目标持续保持连接时会自动清理。

### basic 批次与关闭方式对照

| 场景 | 客户端结果 | 目标端核对与边界 |
|---|---|---|

| abort，立即关闭，独立运行三轮 | 29/30、28/30、30/30；合计 87/90 | 60 条为预期重置行为；恢复流分别为 9/10、8/10、10/10，合计 27/30 完整哈希通过；3 个失败恢复流均仅收到 banner |

上述 basic 各次调用的计划数与实际完成数一致，三轮 abort 独立执行，没有失败后漏跑其他轮次；没有把 60 条预期重置算成 60 次完整负载哈希通过。两个慢读用例各只测试一条；本批未跑其余三种慢读/慢写场景，也未跑 1/4/8 MiB 大数据矩阵。

三个立即关闭恢复失败对应的目标均收到了完整 4,120 字节请求，并提交完整 4,103 字节响应，关闭等待没有超时、错误或强制中止；客户端却都只收到 banner。与 smoke 和慢读的逐流对应一样，目标提交完整响应和正常关闭并不保证官方客户端向本地 TCP 接收方完整交付。

在 basic 完成后的目标汇总中，活动流为 0，累计应用 ACK 实达 43 次，即此前 64 路大流中的 11 次，加 basic 的 30 次恢复、1 次慢读与 1 次 churn 恢复。超时仍为此前大流的 53 次，没有新增；关闭等待、协议、内部错误和准入拒绝计数均为 0。客户端 basic 的关闭等待错误、超时和强制中止也均为 0。这些统计说明已运行的目标流程结束，不把目标产出完成或服务退出当作客户端全部收全。

### 保留 64 个连接，将每流负载降至 64 KiB

该对照使用新增 `--concurrency-size-bytes` 的仓库探针，保持 64 个连接和应用 ACK 关闭方式，将每流负载从 512 KiB 降至 64 KiB，即每方向合计从 32 MiB 降至 4 MiB；目标探针协议未变。

| 项目 | 双端结果 |
|---|---|
| 客户端完整性 | 64/64 完整哈希通过；13.662 秒；无未完成项、客户端总期限触发或关闭等待异常 |
| 应用 ACK | 目标收到并校验全部 64 个 ACK；没有新增 ACK 超时或传输超时 |
| 客户端发送 / 目标接收 | 均为 4,198,656 字节，包含每流 24 字节头及 44 字节应用 ACK |
| 目标提交 / 客户端接收 | 均为 4,194,752 字节，包含每流 7 字节 banner |
| 目标收尾 | 64 条均正常关闭，无关闭等待错误、超时或强制中止；活动流最终为 0 |

对照后目标累计 ACK 为 107 次，即大流 11 次、basic 32 次和本次 64 次；累计传输超时仍为此前大流的 53 次，没有新增协议、内部错误或准入拒绝。这支持将“64 个连接能否建立并完成有限数据”与“64×512 KiB 的集中大负载能否完成”分开验收；它不证明大突发失败已解决，也不能外推到任意 WAN 带宽、时延或拥塞条件。

### CPU 配额观测边界

大流测试之后的检查中，候选累计 CPU 为 3.299912 秒，`nr_throttled=0`、`throttled_usec=0`；basic 完成后累计 CPU 为 4.605948 秒，仍未记录候选 CPU 配额节流。探针单独记录过早先一次 48.252 毫秒的节流。这些是采样时的累计计数，不能当作某一用例的精确 CPU 成本；它们没有提供“候选因 CPU 配额节流而出现这 53 次失败”的证据，也不能单凭这些计数定位网络、缓冲或调度层的具体瓶颈。

腾讯这组结果表明，64 个连接与每方向 32 MiB 的集中负载必须分开描述。已修复的宿主队首阻塞不意味着任意 WAN 负载都能在官方实现的有限发送重试预算内完成，也不意味着所有 FIN 关闭时序都能完整交付。

## 官方客户端静态证据与推断

以下地址仅用于标识本轮 arm64 产物中的静态位置，不代表运行时已经观测到该分支。

| 静态观察 | 可以支持的结论 | 仍不能确认的事项 |
|---|---|---|
| DATA 分支调用 `NWConnection.send`，使用 `contentProcessed` 回调；调用点 `0x10031c6e8` | 向本地 TCP 连接提交发送是异步操作 | 现场每个发送回调何时完成 |
| FIN 分支进入 `closeStream(sendFin: false)`；`0x10031ad6c` 直接调用 `NWConnection.cancel`，未见等待前述完成回调的计数或屏障 | 该实现存在收到 FIN 后立即取消本地连接的路径 | 是否正是某一次截断实际执行的路径，以及剩余字节当时所在的缓冲层 |
| `retryFrame` 失败后以 0.1 秒延迟重试，重试计数最多 50 次，初始发送另计一次 | 名义等待预算约 5 秒，不是 50 或 55 秒；排队和调用自身耗时可以增加总时间 | 现场实际拒绝原因、执行次数及调度延迟 |
| 出站 DATA 的失败回调进入 `closeStream(sendFin: false)` | 存在发送失败后关闭本地连接而不发送 FIN 的路径 | 33 条提前失败流是否实际走过此路径 |
| `libstreamer` 文件发送入口有单次调用大小限制；SCTP 数据通道实现还存在状态检查和 16 MiB 待发队列容量检查 | 底层发送并非总能接受数据，拒绝可以向上返回错误 | 现场 FILE 通道是否触及该容量，以及阻塞由哪一层造成 |

静态 FIN 路径与关闭方式对照共同支持“收到 FIN 后取消尚未完整交付的本地发送”这一待验证解释。有限重试与提前失败样本也值得继续调查，但两者都不构成现场根因的最终证明。宿主构建模式、共享接收阻塞、双方发送/接收缓冲和客户端调度均可能影响背压；已取得的 release 结果与剩余对照必须分别解读。

## 结论与现场收尾

- ThinkPad 保持本轮 `8ac9c08f…` release，服务 enabled/running，重新收到云端 ready 与心跳。已移除本次 runtime debug 覆盖，停止本次探针与采样，两个测试端口均无监听；身份配置只核对 metadata，未读取或复制内容。8 MiB 接收窗口实验没有保留。
- 腾讯已于北京时间 18:41 恢复原 `0.2.57`，原二进制 SHA-256 仍为 `5dcb0b65a95ecbccef1a6394441816322cac5d173bdf6d5ed2801532b608ef92`，服务 enabled/running，云端 ready 与心跳恢复。六个原业务进程及 ssh 的 PID/starttime 均未变化；这证明没有重启这些进程，不等于完整业务性能验收。
