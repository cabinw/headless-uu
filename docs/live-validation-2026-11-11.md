# 2026-11-11 官方 macOS 客户端实测记录

本次使用官方 macOS UU 客户端，验证了 ThinkPad 的实际直连和腾讯硅谷的实际中继。两条路径上的 SSH/SFTP 基本连通，双向合成文件传输的 SHA-256 一致。有限的合成 TCP 测试也有通过项，但异常断开后新流恢复和高并发测试仍出现失败，不能据此宣布完整兼容、长期稳定或生产验收通过。

调查期间还复现并修复了一个可独立证明的旧响应取消缺陷，新增回归测试通过。该缺陷与现场提前 EOF 的因果关系尚未建立；修复后的实测仍有失败。

## 范围与版本

本次使用本机官方 Mac 客户端，宿主侧测试和操作仅涉及 ThinkPad 与腾讯硅谷。绿云未操作。测试使用合成数据、回环目标和限额、限时的负载，不修改 sshd、认证方式、防火墙或网卡配置。腾讯原有其他业务进程的 PID 在最终检查中均未变化。

| 项目 | 本次记录 |
|---|---|
| 官方客户端 | macOS UU 4.44.0（628） |
| ThinkPad 系统与编译器 | Ubuntu 26.04.1；Rust 1.93.1 |
| ThinkPad 初始宿主 | `0.3.0`，基于 `2bb05b8` 的 debug 构建 |
| ThinkPad 后续宿主 | 包含本次取消修复的候选版，已安装并保持在线 |
| 腾讯旧版对照 | `0.2.57` |
| 腾讯临时修复候选 | SHA-256：`5e30ebfb1d597687b6f9955751c294d9c28c52bcb49962e2d9f2804ebdc573d1` |
| 源代码与产物对应关系 | 修复候选由本报告所在提交的 Rust 源码构建；同为 `0.3.0` 的构建用产物 SHA-256 区分，版本号相同不代表二进制相同 |

修复候选也是 debug 构建，仅通过 `strip --strip-debug` 移除调试信息，大小为 44,876,760 字节；本次耗时与资源数据不是 release 构建的性能基准。下文现场时刻均为北京时间（UTC+8）。

实际路径以当前连接的地址脱敏诊断为准：ThinkPad 为 `route=direct`；腾讯临时候选为 `route=relay`，两端候选均为 relay。取得 TURN 参数、设备显示在线或设置代理环境变量本身，都不作为中继证据。

腾讯候选连接记录到的数据通道参数均为 `ordered=true`、`max_packet_lifetime=0`、`max_retransmits=0`。这里记录实现所输出的可靠性参数，不以这些数值推断应用层不会提前关闭，也不把零值直接解释为现场丢包次数。

公开记录只保留版本、计数、时间、哈希一致性、资源统计和地址脱敏的协议状态。真实账号配置、密钥、地址、客户端原始日志和封面素材不随报告发布。smoke 的 0 至 192 KiB 和大数据传输的 1、4、8 MiB 都是合成 TCP 负载大小，不是单个 SCTP 或数据通道帧的大小。

## 独立复现的取消缺陷与自动化回归

旧实现处理未知流的 DATA 时会排队发送 FIN，处理无效 SYN 时会排队发送失败 SYN_ACK。这两条旧响应路径缺少相应的取消令牌覆盖；如果同一流标识随后被新 SYN 复用，排队的旧响应可能影响新流。

本次先用回归测试观察到两项失败，再修复响应的取消关联，并新增三项测试覆盖相关时序。修复还加入了不含地址和凭据的数据通道可靠性参数日志，供现场判断协商结果。

| 平台 | 修复后的完整测试 |
|---|---|
| macOS | 83 项单元测试 + 4 项 CLI 测试 + 2 项封面 CLI 测试，共 89 项通过 |
| Linux | 83 项单元测试 + 4 项 CLI 测试 + 2 项封面 CLI 测试，共 89 项通过 |

这些结果证明被测试的取消时序得到覆盖。它们不证明该缺陷导致了现场提前 EOF，也不能替代下面的官方客户端实测。封面 CLI 测试使用本地测试材料，不代表进行了真实封面上传。

## ThinkPad：实际直连

### SSH/SFTP 与合成 TCP

| 项目 | 结果 | 说明 |
|---|---|---|
| SFTP 上传 | 32 MiB；30.194 秒；SHA-256 一致 | 通过官方客户端映射访问原有 SSH 服务 |
| SFTP 下载 | 32 MiB；32.119 秒；SHA-256 一致 | 下载后再次校验 |
| 基本 smoke | 8/8 通过 | 合成 TCP 测试 |
| 大数据传输 | 1、4、8 MiB 三档，3/3 通过 | 仅代表这三档 TCP 负载 |
| 并发 | 1、8、16 路均通过 | 不外推到更高并发 |
| 连续新建与关闭 | 100 次 churn + 1 次恢复通过 | TCP 流级别；不是 100 次官方客户端或 ICE 重连 |
| 慢目标/慢读等受限负载 | 4 种场景均通过 | 不代表任意拥塞持续时间都可恢复 |

以上耗时是本次路径与负载下的观察值，包含端到端传输的实际开销；没有同条件旧版对照，不据此声称性能提升。

### 异常断开后新流恢复、GUI 取消与关闭

abort 场景通过异常断开或 reset 结束旧 TCP 流，再检查新流能否建立并完成传输；它与官方 GUI 主动取消映射连接是两类测试。

| 场景 | 观察结果 |
|---|---|
| 初始版 abort 首轮 | 29/30 通过 |
| 初始版 abort 两轮重测 | 合计 60/60 通过 |
| 修复候选 abort 三轮 | 合计 88/90 通过，其中异常断开后新流恢复检查为 28/30；仍有失败 |
| 官方 GUI 取消四条慢读目标上传 | 四条 16 MiB 上传连接全部关闭；同时运行的独立 SSH 两次出现 banner 超时，随后在同一会话内恢复 |
| 关闭整个 peer | 8 条空闲连接全部关闭 |
| 宿主重启 | 8 条空闲连接全部关闭；随后在官方客户端点击“重新连接”恢复 |

这些结果同时说明关闭可以传播到连接，以及取消压力下仍可能影响其他连接的及时建立。两次 banner 超时不能忽略，后续恢复也不能将该轮记为全程正常。重启后的恢复包含用户点击“重新连接”，不是无操作自动恢复的证据。

### 64 路并发与对照

UU 映射的两次 64 路并发测试分别为 **36/64**、**28/64** 通过。将测试目标端的 flow deadline 从 60 秒延长到 120 秒未见改善。同类 SSH `-L` 对照为 **64/64** 通过，用时 **4.41 秒**。

该对照支持继续调查 UU 路径上的并发失败，但没有定位到具体一端或具体层次，不能单独归因于官方客户端、宿主、SCTP、ICE 或目标服务。独立修复的旧响应取消缺陷也没有消除所有现场失败。

## 腾讯硅谷：旧版对照与实际中继

### 旧版对照

腾讯 `0.2.57` 的 abort 对照为 **25/30** 通过，其中异常断开后新流恢复检查为 **5/10**。目标端对应的 10 次 echo 均完成。因此旧版也能出现异常断开后新流恢复失败，但目标端完成 echo 并不能证明客户端收到了完整回应，亦不足以定位失败层次。

### 临时修复候选

此连接经实际路径诊断确认为 `route=relay`，两端均使用 relay 候选。

| 项目 | 结果 |
|---|---|
| SFTP 上传 | 16 MiB；29.568 秒；SHA-256 一致 |
| SFTP 下载 | 16 MiB；15.393 秒；SHA-256 一致 |
| 基本 smoke | 8/8 通过 |
| 大数据传输 | 1、4、8 MiB 三档，3/3 通过 |
| 8 路并发 | 8/8 通过 |
| 16 路并发 | 16/16 通过 |
| 连续新建与关闭 | 100 次 churn + 1 次恢复，共 101/101 通过；不是 101 次 ICE 重连 |
| 独立 SSH | 上述各阶段的检查均通过 |
| 客户端慢读 | 第一种 4 MiB 场景失败：4.586 秒时连接提前关闭，客户端累计收到 3,075,719 字节（含 7 字节测试 banner），未收全，无法完成完整性校验 |
| 其余慢场景 | 前项失败触发 fail-fast，后续 3 种未执行 |
| 独立 abort 测试 | 28/30 通过，其中异常断开后新流恢复为 8/10；仍有失败 |
| 在途暂停候选进程约 5 秒后恢复 | 1、4、8 MiB 三档共 3/3 通过哈希校验；测试总耗时 43.274 秒 |
| 官方 GUI 取消四条在途慢读目标上传 | 四条 16 MiB 上传连接全部关闭；期间另一 ThinkPad peer 的 SSH 检查正常 |
| 关闭整个腾讯映射会话 | 8 条空闲连接全部关闭；宿主确认关闭 8 条流，目标服务 active 为 0 |

相关目标服务汇总为 137 次 accepted、37 次 completed、100 次 peer abort、0 次 timeout、0 次 protocol error，检查时 active 为 0。目标端对应的 4 MiB 发送流程已完成，而客户端未收全；这不能等同于端到端传输成功，也没有定位出具体哪一端或哪一层提前结束。不能将此轮记录为慢场景或全矩阵通过。

在途暂停测试的时间戳为：客户端于 `16:18:04.404` 开始，进程于 `16:18:08.870` 收到 STOP、`16:18:13.886` 收到 CONT，暂停约 5.016 秒，确实与传输重叠。较早 `16:16:48` 的一次暂停发生在上一条数据流结束后，只计为空闲暂停，不作为在途恢复证据。暂停进程并不等同于任意网络中断、切网或 ICE 重连。

候选进程的采样峰值为 FD 27、RSS 32,020 KiB、PSS 29,527 KiB，随后 FD 回落到 12；最终采样为 FD 11、RSS 30,940 KiB、PSS 28,448 KiB、线程 2。恢复旧 UU 后，原有其他业务进程 PID 仍均未变化。

本次 ThinkPad 和腾讯测试的路径、文件大小与环境不同，不能直接比较耗时得出直连或中继优劣，也不能据此宣称候选版快于旧版。

当前能支持的结论是：指定官方 macOS 版本在本次实际直连和实际中继路径上，完成了 SSH/SFTP 基本通信及有哈希校验的双向文件传输；部分合成 TCP 与连接关闭场景通过；一个独立可复现的取消缺陷已有回归修复。

仍未完成的验收包括现场提前 EOF 的根因、异常断开后新流的可靠恢复、64 路并发失败、其他官方客户端版本与 Windows 客户端，以及更长时间和更多网络条件下的稳定性验证。测试没有证明自动重连、无限次重连无泄漏或生产负载下的性能提升。新增回归通过与已完成的现场通过项，均不应覆盖这些已知边界。
