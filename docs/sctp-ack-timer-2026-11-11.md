# 2026-11-11 SCTP 延迟 ACK timer 修复

本阶段基于已推送的 `main` 提交 `668e39d`，独立修复 `webrtc-sctp 0.9.1` 延迟 ACK timer 的两类生命周期缺陷。原版可稳定复现回归失败，最小修复后通过；本轮官方客户端实测仍出现 64 路 WAN 大突发失败和 FIN 尾部截断，不能把独立 timer 红绿证据当作[第一阶段现场问题](extreme-validation-2026-11-11.md)的根因确认或完整修复。

## 缺陷与最小修复

| 缺陷 | 原行为 | 修复后的行为 |
|---|---|---|
| 自然到期后不能重新启动 | 回调结束后仍保留发送端句柄；`start()` 只判断句柄是否存在，因此下一次孤立 DATA 可能无法重新启动延迟 ACK timer | 根据本代取消 receiver 是否关闭判断运行状态；回调完成后，在释放 observer 锁前关闭本代 receiver，下一次 DATA 可重新启动 |
| 到期后等待 observer 锁时取消失效 | timer 到期后不再监听取消；即使随后 `stop()`、释放 timer 或启动新代，旧回调仍可能在取得锁后执行 | 等待 deadline 和等待 observer 锁时都优先处理取消，取锁后再次检查取消状态 |

每次 `start()` 使用独立取消通道。旧回调完成时只关闭自己的 receiver，不调用共享 observer 上的 `stop()`，因此不会误停新一代。释放 timer 会丢弃发送端，使仍在睡眠或等待锁的任务退出；已经进入的回调不能撤销，这是明确保留的边界。实际 association 的启停操作受同一 observer mutex 保护。

运行源码仅修改 [`vendor/webrtc-sctp/src/timer/ack_timer.rs`](../vendor/webrtc-sctp/src/timer/ack_timer.rs)。与上游包逐一比对 71 个源文件，只有该文件存在差异，另新增补丁说明；来源、许可证、包校验值和补丁范围见 [vendor PATCHES.md](../vendor/webrtc-sctp/PATCHES.md)。默认间隔仍为 200 毫秒，没有改变消息线格式、接收窗口、队列限额、拥塞策略或端口映射 FIN 处理。[RFC 9260 §6.2](https://www.rfc-editor.org/rfc/rfc9260.html#section-6.2)建议在未确认 DATA 到达后 200 毫秒内生成确认，并规定 `SACK.Delay` 的最大配置值不得超过 500 毫秒；本补丁修复计时器生命周期，没有新增运行时延迟保证。

## 三种确认不能混淆

| 名称 | 层次与含义 |
|---|---|
| SCTP SACK | SCTP 传输层确认 DATA chunk；本次修改其延迟确认 timer，不证明本地 TCP 应用已读到数据 |
| UU DATA_ACK | UU 端口映射消息类型 4；现有双方处理仍忽略它，本次没有启用或扩展其语义 |
| 探针应用 ACK | 合成 TCP 目标使用的 44 字节确认，包含合成流标识和哈希；客户端 `ok` 不足以证明送达，仍需目标端确认计数 |

## 回归证据

[`tests/sctp_ack_timer.rs`](../tests/sctp_ack_timer.rs) 的前 7 项直接编译实际 vendored timer，通过 Tokio 虚拟时钟和 observer mutex 检验生命周期，不创建网络连接。

| 同一组 7 项测试 | 结果 |
|---|---|
| 未修改的上游 timer | 6 项失败、1 项通过 |
| 修复后的 timer | 7 项通过 |

覆盖自然到期后的重复重启、到期后锁等待中的取消、旧代与新代隔离、普通启停、timer 释放，以及已进入的旧回调完成时不关闭替代代次。独立只读审查未发现该最小方案的阻塞问题。

第 8 项 `sparse_sctp_data_repeatedly_drains_on_delayed_ack_before_retransmission` 使用真实 SCTP `Association`、DATA 和 SACK 处理，底层是内存 packet pipe，没有 socket、ICE、DTLS 或官方客户端。保持默认 Normal ACK 模式，依次发送 3 轮各 1 字节的孤立消息，逐字节核验接收内容，每轮仅推进 200 毫秒虚拟时钟，并等待发送缓冲因确认而排空，再发送下一轮。该负载避免高吞吐下第二个包触发立即 SACK、掩盖 timer 重新启动缺陷。

| 同一项真实 SCTP 集成回归 | 结果 |
|---|---|
| 未修改的上游 SCTP 包 | 第 1 轮在 200 毫秒排空；第 2 轮到 400 毫秒仍有 1 字节待确认，缺少本轮 SACK，触发防挂 watchdog 后失败 |
| 修复后的 SCTP 包 | 3 轮分别在 200 / 400 / 600 毫秒排空，接收内容全部一致 |

修复版累计发送 DATA 包 96 字节、SACK 包 84 字节，恰好对应 3 个 32 字节 DATA 包和 3 个 28 字节 SACK 包；这些是含协议封装的包大小，应用负载合计仅 3 字节。总虚拟时间 600 毫秒小于最小 T3 重传超时 1000 毫秒，且精确包字节计数没有额外 DATA，因此本测试的排空不依赖重传。5 秒真实时间 watchdog 仅防止测试挂起，不是现场 ACK 延迟验收指标。

## 已确认范围与剩余问题

本次确认了独立 timer 生命周期缺陷、取消代次隔离和稀疏 SCTP DATA 的确认恢复，完成两平台自动化回归及上述有限现场负载。应用 ACK 是诊断探针协议，用来控制目标关闭时机，不能作为普通 SSH/SFTP 或任意 TCP 服务的生产修复，也没有启用 UU DATA_ACK。

直接路径和 relay 路径仍有立即关闭后的恢复流及慢读截断，relay 的 64 × 512 KiB 突发仍失败。目标在 120 秒释放连接来自合成探针期限，不能证明 daemon 会自动回收没有 FIN 的孤儿流；真实目标若继续保持连接，目前已证明的清理边界仍是 peer / session shutdown。以上结果不构成完整官方兼容或长期稳定性验收通过。
